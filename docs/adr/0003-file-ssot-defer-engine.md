# ADR-0003 · 파일을 SSOT 로, 그래프 엔진 선택은 유보

- **상태**: 채택 (2026-07-30)
- **관련**: [`../architecture/02-storage-topology.md`](../architecture/02-storage-topology.md)

## 맥락

그래프 데이터를 어디에 저장할 것인가. 그래프 DB 를 지금 도입할지, 파일로 시작할지.

## 결정

**Git 저장소의 YAML/JSONL 파일이 단일 진실 원천(SSOT)이다.** 그래프 엔진·검색 인덱스는 빌드 산출물이며, 언제든 재생성 가능하다. 엔진 선택은 규모가 요구할 때까지 유보한다.

## 근거

지식베이스에서 가장 중요한 속성은 질의 성능이 아니라 **검토 가능성**이다. 잘못된 사실이 들어오는 것을 막는 것이 빠르게 조회하는 것보다 우선한다.

| 속성 | 파일(Git) | 그래프 DB |
|---|---|---|
| 변경 이력 | 커밋에 내장 | 별도 구현 |
| 사람 검토 | PR diff | 어려움 |
| "누가 왜 바꿨나" | 커밋 메시지 | 별도 감사 로그 |
| 이식성 | 완전 | 벤더 종속 |
| 질의 성능 | 나쁨 | 좋음 |

질의 성능은 빌드 산출물이 해결한다. 초기 규모(노드 1,200~5,000)에서는 메모리 적재로 충분하다.

## 결과

- `build_graph` 가 `kb/**` → `build/graph.json` + SQLite + 인덱스를 생성
- 빌드는 **재현 가능**해야 한다 (외부 네트워크 호출 금지)
- `kb/derived/` 의 생성물은 CI 가 재생성 결과와 대조 — 손으로 고친 생성물을 검출
- 엔진 전환 시점: 노드 20,000 초과 또는 동시 편집자 5인 초과
- 전환 후에도 파일은 SSOT 로 유지, DB 는 캐시

## 대안

- **처음부터 그래프 DB** — 조기 최적화. 스키마가 아직 흔들리는 단계에서 DB 마이그레이션 부담을 진다.
- **관계형 DB** — 관계 유형 추가마다 스키마 변경.
- **문서 DB** — 그래프 순회 질의가 불편하고, 파일 대비 검토 이점이 없다.
