Travel Rule Protocols — 기술 표준 / 메시징 프로토콜

Travel Rule 을 **실제로 어떻게** 메시지로 주고받는가. 이 글을 읽고 나면 "IVMS 101 은 데이터 모델이고 TRISA·TRP 는 프로토콜이다"라는 구분을 정리하고, 관할별 검증 규칙을 조문 문언에 맞게 짜는 법을 이해하게 됩니다..

이 파일의 역할: Travel Rule 의 기술 상세 — IVMS 101.2023 데이터 모델·관할별 검증 규칙·프로토콜 공개 사실·상호운용 설계. 법적 근거는 ../2-regulations/korea-fiu-act.md §5, 개념·관할 비교·운영 흐름은 ../3-crypto-aml/travel-rule.md 참조. 근거 도시에: ../../research/2026-10-travel-rule.md §4.11.

TL;DR

  • 데이터 모델 = IVMS 101.2023(2023-08 발행, interVASP ISWG 유지, 2024-06-04 갱신 공표). "IVMS101 v2" 는 없음
  • 전송 프로토콜은 여러 개: TRP(OpenVASP Association 관리), TRISA, 솔루션 네트워크(VerifyVASP·CODE·GTR·Sygna 등). 어느 것도 모든 상대방을 덮지 못함
  • 관할별 필수 항목은 조문이 정함 — EU TFR 제14조(1)은 주소 또는 생년월일·출생지, IVMS 101.2023 제약 C1 도 자연인 송신인에 4종 중 1개 이상. "EU 모든 필드 필수"는 틀림
  • 미국 기준은 31 CFR 1010.410(f) USD 3,000 이상 그대로. $250 하향안은 2025-04-16 철회, "$1,000 개정 제안"은 존재 확인 안 됨
  • 메시지 실패율·지연·SLA·오류 분포에 대한 공개 벤치마크는 없음 — 이 문서의 이전 판 수치는 출처가 없어 삭제

1. 표준 vs 프로토콜 vs Discovery — 3개를 분리해서 이해하라

왜 혼동이 자주 일어나나

Travel Rule 구현 용어 혼동의 대부분은 "메시지에 뭘 넣을지"(데이터 모델), "어떻게 주고받을지"(프로토콜), "누구에게 보낼지"(Discovery) 가 서로 다른 층위라는 걸 놓쳐서 생깁니다. 같은 IVMS 101 페이로드를 다른 프로토콜로 주고받을 수 있습니다.

구분 역할 예시
메시지 데이터 모델 무엇을 담는가 (필드 구조) IVMS 101.2023
전송 프로토콜 어떻게 주고받는가 (네트워크) TRP, TRISA, 솔루션 네트워크
VASP Discovery 상대가 누구인가 (라우팅) 블록체인 분석, Directory, LEI, DTI

2. IVMS 101.2023 — 데이터 모델 상세

정체성

  • IVMS 101 — interVASP 데이터 모델 표준. 2020-05 원판은 JWG 가, 현행 「IVMS 101.2023, interVASP data model standard Issue 1 FINAL」(Published August 2023)은 GDF·OpenVASP·VASPnet 이 2023-04 결성한 interVASP Standards Working Group(ISWG, GDF Open Standards Council 산하)이 유지(interVASP)
  • ISWG 는 2024-06-04 갱신을 공표: "The ISWG released an update to IVMS 101 on 4 June 2024."
  • 표준 문서에는 JSON/XML 스키마가 포함되지 않습니다 — 스키마는 구현체가 따로 관리합니다
  • 2020→2023 변경 목록(errata)은 이 저장소가 확인하지 못했습니다

2023판에서 정식화된 것 (원문 확인)

출처: IVMS 101.2023 PDF(npm 패키지 미러 — 패키지 버전 2.0.0 은 표준 판 명칭이 아님)

항목 내용

LEIText ISO 17442, 20자
NationalIdentifierTypeCode ISO 20022 TypeOfIdentification4Code 제한, LEIX 포함
제약 C1 자연인 송신인: geographicAddress(GEOG·HOME·BIZZ) 및/또는 customerIdentification 및/또는 nationalIdentification 및/또는 dateAndPlaceOfBirth — 1개 이상 필수

C1 원문: "If the originator is a NaturalPerson either (geographicAddress with an addressType value of 'GEOG' or 'HOME' or 'BIZZ') and/or customerIdentification and/or nationalIdentification and/or dateAndPlaceOfBirth is required."

NaturalPerson 필드 — "선택"이 아니라 "택1 이상"

이전 판은 DateAndPlaceOfBirth 를 단순 "선택"으로 적었습니다. 2023판 C1 에 따르면 주소·고객식별번호·국가식별번호·생년월일·출생지는 각각은 선택이지만 넷 중 하나는 반드시 있어야 합니다.

관할별 차이 처리 — 조문 문언 기준

관할 조문 송신인 필수 항목(요지)
🇪🇺 EU TFR 제14조(1) 성명·DLT 주소·계정번호·주소 또는 생년월일·출생지·LEI 등. 금액 간소화 없음
🇬🇧 영국 MLR reg 64C(5)·(6) (5) 성명, 계좌번호 또는 고유거래식별자 / (6) 개인: 고객식별번호·주소·신분증 번호·생년월일+출생지 중 하나 — (4)항 금액(2026-06-30~ £800, 그 전 1,000 euros) 이상
🇸🇬 싱가포르 PSN02 ¶13.4·¶13.6 ≤S$1,500: 4항목 / >S$1,500: 신원확인·검증 + 주소·고유식별번호·생년월일 중 하나
🇰🇷 한국 2027-02-19~ 시행령 §10-10 ②·③ 동시: 성명·가상자산주소 / 요청 시 3영업일: 주민등록번호(법인등록번호)·여권번호·외국인등록번호
🇺🇸 미국 31 CFR 1010.410(f) USD 3,000 이상 이체지시: 송신인 성명·계좌번호·주소·금액·실행일·수취 금융기관

근거: EBA/GL/2024/11 · MLR reg 64C · MAS PSN02 · 법제처 시행예정 판본 · Cornell LII.

실무 포인트

검증기에서 가장 어려운 부분은 관할별 필수 항목을 조문 문언대로 옮기는 것입니다. "택일" 조문(EU 주소 또는 생년월일, 영국 (6)항 중 하나)을 "전부 필수"로 구현하면 적법한 메시지를 거절하고, 금액 구간을 시점 없이 하드코딩하면 과거 거래 재검증이 틀립니다. 누락 시 거절할지 보완 요청할지는 회사 정책으로 명문화하되, 근거 조문(영국 64C(9), 싱가포르 ¶13.11·¶13.14, EU EBA GL §4.7)을 함께 적어 두십시오.

N. IVMS 101 Validator — 관할별 구현

N.1 관할별 규칙 — 택일 조건과 시점을 표현한다

검증 실패 원인 비율에 대한 공개 통계는 없습니다. 아래는 조문 문언을 코드로 옮기는 구조 예시입니다(필드 경로는 단순화).

from datetime import date

DEPTH_THRESHOLDS = {

C1_ANY_OF = ["originator.geographicAddress",      # addressType GEOG/HOME/BIZZ

이전 판의 규칙 중 다음은 근거가 없거나 틀려서 뺐습니다: "EU dateOfBirth·placeOfBirth REQUIRED"(TFR 은 주소와 택일), "US 2025 개정 제안 $1,000"(존재 확인 안 됨, $250 안은 2025-04-16 철회), "KR nationalIdentification HASHED"(2027 판 제3호는 요청 시 정보 제공을 정할 뿐 해시 전송 근거 없음), "KR 이름 한글+영문 병기 필수"(조문 근거 없음).

N.2 Validator 구현 (Python pseudocode)

def validate_ivms101(msg: dict, jurisdiction: str, transfer_date: date) -> ValidationResult:
    errors = []
    rules = JURISDICTION_RULES[jurisdiction]

    for path in rules.get("required", []):
        if not get_nested(msg, path):
            errors.append(f"Missing required: {path}")

    for group in rules.get("one_of", []):
        if not any(get_nested(msg, p) for p in group):
            errors.append(f"Need at least one of: {group}")

    # IVMS 101.2023 C1 — 관할과 무관한 데이터 모델 제약
    if is_natural_person(msg, "originator") and not any(get_nested(msg, p) for p in C1_ANY_OF):
        errors.append("IVMS 101.2023 C1: address/customerId/nationalId/DOB 중 1개 이상 필요")

    # 심화 기준은 이전 시점의 구간으로 판정
    tier = active_threshold(DEPTH_THRESHOLDS.get(jurisdiction, []), transfer_date)
    if tier and exceeds(msg["amount"], tier):
        errors += check_depth_fields(msg, jurisdiction)

    return ValidationResult(passed=not errors, errors=errors)

N.3 카운터파티 이름 일치 검증 (Fuzzy Matching)

IVMS 메시지의 originator·beneficiary 이름이 자사 KYC DB 와 일치하는지 검증합니다. 로마자 표기 다양성 때문에 정규화가 필요합니다. 유사도 임계값은 조문이 정하지 않으므로 자사 데이터로 보정해야 하며, 아래 값은 예시입니다.

from jellyfish import jaro_winkler_similarity

def verify_name_match(submitted: str, kyc_db: str, threshold: float) -> bool:
    # threshold 는 자사 오탐·미탐 실측으로 정한다 (공개 기준값 없음)
    return jaro_winkler_similarity(normalize(submitted), normalize(kyc_db)) >= threshold

def normalize(name: str) -> str:
    name = name.lower().strip()
    for old, new in [("-", ""), (",", "")]:
        name = name.replace(old, new)
    return " ".join(name.split())

M. Protocol Interoperability — 라우팅·재시도·Fallback

M.1 경로별 지연

이전 판의 경로별 p50 지연(~2~3초, ~5~10초 등) 표는 출처가 없어 삭제했습니다. 지연·타임아웃은 상대 네트워크와 계약 조건에 따라 다르므로 자사 측정값을 쓰십시오.

M.2 실패 모드 + 재시도 전략 (설계 예시)

class TravelRuleRouter:
    MAX_RETRIES = 3          # 예시 값
    BACKOFF_BASE = 2         # 지수 백오프(초), 예시 값
    # 프로토콜별 타임아웃은 상대 네트워크 계약·실측으로 정한다 (공개 SLA 없음)

    async def send(self, msg, target_vasp: str):
        protocol, endpoint = await self.discover_route(target_vasp)
        for attempt in range(self.MAX_RETRIES):
            try:
                return await self._send(msg, protocol, endpoint,
                                        timeout=self.timeouts[protocol])
            except TimeoutError:
                await asyncio.sleep(self.BACKOFF_BASE ** attempt)
            except AuthError as e:
                if e.code == "cert_expired":
                    await self.refresh_cert()
                    continue
                raise
            except IVMS101ValidationError as e:
                msg = self.mapper.fallback(msg, target_jurisdiction=e.jurisdiction)
            except UnreachableError:
                return await self.handle_unreachable(msg, target_vasp)
        raise UndeliverableError(target_vasp)

M.3 Sunrise Issue (미연결 카운터파티) 처리 — 정책과 근거 조문

def handle_sunrise(msg, target_vasp: str, policy: str):
    discovered = await discover_vasp(target_vasp)
    if discovered:
        return await send_tr(msg, discovered)

    if policy == "HOLD":
        # 보류 후 재시도. 보류 기간은 조문이 정하지 않음 — 자사 정책
        await queue.delay(msg, target_vasp)
        return Status.PENDING
    elif policy == "COLLECT_AND_RECORD":
        # 영국 FCA 2023-08-17: 미시행 관할로는 정보를 수집·검증·보관한 뒤 이전 가능
        # FATF 2021 para 200–201: 계약·사업관행, first-party 이전 한정 등 위험기반 대응
        await audit_log.record(msg, reason="sunrise_counterparty")
        return Status.SENT_WITH_RECORD
    elif policy == "REJECT":
        # 영국 reg 64C(9), 싱가포르 PSN02 ¶13.11 — 완전 준수 불가 시 이전 금지
        return Status.REJECTED

관할별로 허용되는 정책이 다릅니다. 영국·싱가포르에서 송신 측이 정보를 갖추지 못하면 이전 자체가 금지되고, EU 는 sunrise 상대를 고위험 요소로 분류하며 반복 누락 기관을 식별 후 3개월 안에 보고하게 하고(EBA GL §4.5·§4.7), 한국은 2027-02-19 부터 상대 VASP 의 트래블룰 이행을 저위험 허용 요건으로 둡니다(고시 §28-2②).

3. 주요 전송 프로토콜 — 공개 사실 (2026-10-21)

A. TRP (Travel Rule Protocol)

  • 관리: OpenVASP Association(Zug)이 TRP 표준을 관리하는 협회. 주간 TRP Working Group, GitLab 공개 사양(CC BY-SA 4.0)

  • 현행 TRP 버전 번호는 사이트에 표시되지 않음. Notabene 는 "Every Notabene customer has a live TRP 1.0 endpoint" 라고 밝힘(B)

B. OpenVASP

이전 판의 "OpenVASP: Ethereum·ENS·Whisper 기반, 활용도 낮음"은 2020년 이전 설계 서술입니다. 2026-10-21 기준 OpenVASP Association 은 TRP 의 모체 협회이며 TRP 는 활동 중입니다(OpenVASP).

C. TRISA (Travel Rule Information Sharing Architecture)

  • gRPC/protobuf 기반 오픈소스 프로토콜 + Global Directory Service(B)
  • 오픈소스 노드 Envoy 가 TRISA 와 TRP 를 모두 지원한다고 밝힘(B)
  • GitHub trisacrypto/trisa 공개. 2026-10-21 trisa.io 는 응답하지 않음 — 접속 불가만으로 운영 중단을 추정하지 말 것
  • 근거: trisa.dev, GitHub

D. VerifyVASP

  • 홈페이지에 TravelRule API·VerifyName API·VerifyWallet 제품 표시(B). 운영 주체는 홈페이지에 명시되지 않음
  • 근거: VerifyVASP

E. CODE

  • 근거: CODE

F. Notabene

  • 제품 SafeTransact·Notabene Flow·TAP, OpenVASP 회원, TRP 1.0 엔드포인트 지원(B). 2026-07-23 Ripple 전략투자 발표(금액 비공개, B)

I. 기타

  • Sumsub Travel Rule — 자체·GTR·CODE·TRP·Sygna 5개 프로토콜 연동 표시(B)(Sumsub)

실무 포인트

프로토콜 선택은 고객의 출금 상대방이 어느 네트워크에 있는가로 정합니다. 어느 네트워크도 모든 상대방을 덮지 못하므로, 선택과 별개로 미연결 상대방 정책(§M.3)을 먼저 정해야 합니다. 가격·커버리지 비교는 공개 1차 근거가 없어 이 문서에서 다루지 않습니다.

4. 분산형 vs 폐쇄형 — 설계 트레이드오프

두 모델은 신뢰를 어디에 두느냐가 다릅니다. 아래는 구조적 비교이며 어느 쪽이 낫다는 평가가 아닙니다.

항목 양자 간 오픈 표준 (TRP, TRISA) 회원제 네트워크 (솔루션 네트워크)
참여 사양 공개, 각자 구현 네트워크 가입
신뢰 모델 인증서·양자 간 확인 네트워크 운영자의 회원 검증
라우팅 상대 식별을 별도로 해야 함 네트워크 내 디렉터리
운영 책임 각 VASP 운영자 + 회원

실무 포인트

한국 시장에 들어오는 외국 VASP 는 국내 사업자가 연결된 네트워크와의 경로를 먼저 확인해야 합니다. 2027-02-19 부터는 한국 VASP 가 해외 VASP 의 AML·트래블룰 이행을 평가해 허용 등급을 정하므로(고시 §28-2), 메시지 경로뿐 아니라 평가에 필요한 자료(인허가·트래블룰 이행 근거) 를 함께 준비하는 편이 낫습니다.

5. VASP Discovery — 지갑 주소가 어느 VASP 인가

문제

FATF 2021 가이던스 para 197(a): "the FATF is not aware of any technically proven means of identifying the VASP that manages the beneficiary wallet exhaustively, precisely, and accurately … from the VA address alone"(FATF 2021 RBA 가이던스).

수단

  • 블록체인 분석·제3자 데이터·메시징 식별자 — EBA GL ¶77~78 이 자기수탁 판단 수단으로 열거. 불가하면 고객에게 직접 확인하고, 상대가 CASP 로 판명되면 상대 CASP 를 정확히 식별
  • 네트워크 디렉터리 — TRISA GDS, 솔루션 네트워크 회원 목록
  • LEI(ISO 17442) — IVMS 101.2023 의 법인 식별(C9~C11)
  • DTI(ISO 24165) — 토큰 식별자. TRP 가 호환을 명시

실무 포인트

라벨 DB 로 1차 식별하고, 모호하면 디렉터리 조회, 그래도 안 되면 고객 확인·수동 검토로 넘기는 것이 EBA GL ¶77~78 의 순서와도 맞습니다. 7차 TU 는 상대방 VASP 식별을 "completely and accurately" 수행하고 소매고객으로 위장한 역외 VASP 계정을 탐지하라고 권고합니다(7차 TU PDF).

6. 호환성 / Interoperability 문제

Sunrise Issue (미시행 관할 카운터파티)

일부 관할은 Travel Rule 을 시행하지 않아 메시지를 받을 수단이 없습니다. 2026-07-16 기준 FATF 조사 109 관할 중 91(83%)이 입법, 11 관할이 입법 진행 중입니다. 대응 정책은 §M.3.

Protocol Mismatch

양쪽이 다른 네트워크를 쓰면 직접 호환되지 않습니다. 해결은 (1) 상호운용 연동을 표시한 네트워크 이용, (2) 복수 네트워크 동시 가입, (3) 자체 멀티 프로토콜 어댑터입니다.

Data Model Version Mismatch

PayloadVersionCode 가 101 과 101.2023 으로 나뉩니다. 수신 측은 두 값을 모두 처리하고, 2023판 제약(C1·C9~C11)을 어느 버전 메시지에 적용할지 정책으로 정해야 합니다.

실무 포인트

EU 에서는 EBA GL ¶24 의 기술적 한계 보완 유예가 2025-07-31 에 끝났습니다. 2025-08-01 이후에는 프로토콜 간 변환에서 생긴 필드 누락을 기술적 한계로 정당화할 수 없습니다(EBA/GL/2024/11).

7. 한국 시장 운영 패턴

국내 VASP → 국내 VASP
  └─ ~2027-02-18: 100만원 이상만 정보제공 / 2027-02-19~: 모든 이전
국내 VASP → 해외 VASP
  └─ 2027-02-19~: 고시 §28-2 평가 — 저위험 허용 / 그 외 동일인 간만 / 고위험 제한
국내 VASP → 자기수탁 주소
  └─ 2027-02-19~: 동일인 간만 허용 (증명 방법 미지정)
수탁업자 내부 지갑 간 이동
  └─ "다른 가상자산사업자에게 이전" 이 아니므로 정보제공 대상 아님

근거: 법제처 시행예정 판본, 감독규정 FIU 고시 제2026-2호. 2027-02-19 규정은 2026-10-21 기준 enacted-not-in-force 이고, 고시 §28-2 시행일은 기산점 문제로 미확정입니다.

실무 포인트

시행령 §10-10 은 "가상자산사업자가 다른 가상자산사업자에게 가상자산을 이전하는" 경우를 규율합니다. 같은 사업자의 콜드월렛 간 이동은 이 문언에 들어오지 않으므로, 정책에 이 구분을 명문화해 두면 불필요한 메시지 발송을 막을 수 있습니다.

자주 나오는 오해

  • "IVMS101 만 지원하면 Travel Rule 완성" — 데이터 모델은 기본입니다. 실제로는 프로토콜 선택 + VASP Discovery + 미연결 정책이 함께 있어야 합니다
  • "IVMS101 v2 로 곧 바뀐다" — 현행판 명칭은 IVMS 101.2023 입니다. npm 패키지 버전 2.0.0 과 혼동하지 마십시오

  • "게이트웨이 = 특정 프로토콜" — 허브는 라우터이고, 실제 전송은 하부 프로토콜이 담당합니다
  • "메시지 15년 보관이 법정 의무" — 이 저장소는 그 근거 조문을 확인하지 못했습니다. 관할별 기록보존 조문을 직접 확인하십시오

Travel Rule 벤더 — 공개 사실 지도

메시징 프로토콜·Travel Rule 솔루션 시장을 **공개 자료로 확인되는 사실만** 정리합니다. 이 글을 읽고 나면 각 네트워크가 무엇이고 누가 운영하며 서로 어떻게 연동된다고 밝히는지, 그리고 무엇이 확인되지 않았는지를 구분할 수 있게 됩니다. 벤더 간 우열·추천·가격은 다루지 않습니다..

notes/7-vendors/travel-rule-vendors.md
보조 읽기 · Day 26 notes/7-vendors/travel-rule-vendors.md

TL;DR

  • 모델은 셋: 양자 간 오픈 표준(TRP·TRISA) · 회원제 솔루션 네트워크(VerifyVASP·CODE·GTR·Sygna 등) · 멀티프로토콜 연동을 표시하는 솔루션(Sumsub·Notabene·CODE 등)
  • 2026-10-21 기준 정정: OpenVASP Association 은 TRP 표준을 관리하는 협회(이전 판의 "Ethereum·ENS·Whisper 기반"은 2020년 이전 설계), GTR 운영 주체는 Infozone Technologies(싱가포르)(이전 판의 "BitGo 등 컨소시엄"은 근거 없음), 데이터 모델 현행판은 IVMS 101.2023("IVMS101 v2" 없음)
  • 네트워크 규모(VASP 수)·가격·성공률·가입 소요기간은 공개 1차 근거가 없거나 자사 주장이라 이 문서에서 뺐습니다
  • 벤더 선택의 기준은 "누가 1위인가"가 아니라 우리 출금 상대방이 어느 네트워크에 있는가와 미연결 상대방 정책입니다

1. 시장 구조 — 3가지 모델

세 모델의 차이

  • 양자 간 오픈 표준 — 사양이 공개돼 있고 각 VASP 가 구현합니다. TRP 는 "Bilateral exchange of encrypted data (VASP-to-VASP). No data or metadata is ever exchanged with any third party" 라고 설명합니다(OpenVASP TRP).
  • 회원제 솔루션 네트워크 — 운영자가 회원을 검증하고 디렉터리를 제공합니다.
  • 멀티프로토콜 연동 — 한 솔루션이 여러 네트워크와의 연동을 표시합니다. 허브는 라우터이고, 실제 전송은 하부 프로토콜이 담당합니다.

2. 주요 벤더·프로토콜 — 공개 사실

아래는 2026-10-21 각 자사 페이지 열람 결과입니다(T3, 확신도 B). 네트워크 규모 수치는 자사 주장이라 인용하지 않습니다.

A. Notabene

  • 제품: SafeTransact·Notabene Flow·TAP. OpenVASP 회원. "Every Notabene customer has a live TRP 1.0 endpoint."
  • 2026-07-23 Ripple 의 전략투자(금액 비공개) 발표
  • 근거: Notabene About, Notabene TRP, Ripple 투자 발표

B. VerifyVASP

  • 홈페이지에 TravelRule API·VerifyName API·VerifyWallet 제품 표시
  • 운영 주체는 홈페이지에 명시되지 않음. 이전 판의 "람다256 + Chainalysis 합작" 지분 구조는 2026-10-21 공개 1차 근거로 확인되지 않았습니다
  • 근거: VerifyVASP

C. CODE (CodeVASP)

  • 운영: CODE Inc. 홈페이지 상호운용 목록에 CodeVASP·VerifyVASP·GTR·Sumsub·Sygna·Notabene·CryptoSwift 표시
  • 2026-03-25 비호스팅 지갑 식별 솔루션 게시
  • 이전 판의 "빗썸·코빗·코인원 3사 합작" 지분 구조는 홈페이지에서 확인되지 않음(2022 보도 기반으로만 전해짐)
  • 근거: CODE

D. Sumsub Travel Rule

  • 자체·GTR·CODE·TRP·Sygna 5개 프로토콜 연동 표시. 비호스팅 지갑은 자체 프로토콜과 블록체인 분석 파트너를 통한 "multiple verification methods"로 검증한다고 적음
  • 이전 판의 "본사 영국"은 이번 조사에서 확인하지 못해 삭제
  • 근거: Sumsub Protocols

E. Sygna (CoolBitX)

  • Sygna Bridge 2.0·IVMS101 지원 표시. Sumsub·GTR·CODE 가 지원 프로토콜로 올림
  • 이전 판의 "일본·동남아 거래소 다수"는 근거가 없어 삭제
  • 근거: Sygna

F. Global Travel Rule (GTR)

  • 운영: Infozone Technologies Pte. Ltd.(싱가포르). 홈페이지에 얼라이언스 회원 목록과 지원 프로토콜(Code·Sumsub·Sygna·Fireblocks), 제품(API·Manual·Wallet Verification·Out-Of-Network) 표시
  • 이전 판의 "BitGo 등 컨소시엄, 일부 미국·중남미"는 근거가 없어 삭제
  • 근거: GTR

G. TRISA

  • gRPC/protobuf 기반 오픈소스 프로토콜 + Global Directory Service. 오픈소스 노드 Envoy 가 TRISA 와 TRP 를 모두 지원한다고 밝힘
  • 2026-10-21 trisa.io 는 응답하지 않음 — 접속 불가만으로 운영 중단을 추정하지 말 것
  • 이전 판의 "일부 LATAM, 신흥시장 사용"은 근거가 없어 삭제
  • 근거: trisa.dev, GitHub trisacrypto/trisa

H. TRP (Travel Rule Protocol) · OpenVASP

  • OpenVASP Association(Zug)이 TRP 표준을 관리. 주간 TRP Working Group, GitLab 공개 사양(CC BY-SA 4.0), ISO 24165(DTI)·IVMS101 호환. TRP 벤더로 21 Analytics 등을 듦
  • 현행 TRP 버전 번호는 사이트에 표시되지 않음
  • 근거: OpenVASP, OpenVASP TRP, GitLab

I. 21 Analytics

  • 도메인을 21analytics.ch → 21analytics.co 로 이전(301). AOPP(주소 소유 증명 프로토콜) 용어집 운영
  • 근거: 21 Analytics AOPP

실무 포인트

위 사실은 모두 자사가 자기에 대해 밝힌 것입니다. 연동 목록은 "연동을 표시함"이지 품질·커버리지·안정성을 뜻하지 않습니다. 실제 도입 판단은 우리 출금 상대방 목록을 들고 각 네트워크에 직접 확인해야 합니다.

3. 벤더 선택 — 확인할 질문

이전 판의 "회사 유형별 추천" 표는 우열 평가여서 삭제했습니다. 대신 규범이 요구하는 것에서 출발한 질문 목록입니다.

질문 왜 필요한가 근거
우리 출금 상대방 상위 N 곳이 이 네트워크(또는 연동 네트워크)에 있는가 미연결이면 정보를 보낼 수 없음 FATF 2021 para 200–201 (sunrise 대응)
IVMS 101.2023 의 C1·LEI 제약(C9~C11)을 검증하는가 현행 데이터 모델 제약 IVMS 101.2023
관할별 금액 구간을 시점과 함께 설정할 수 있는가 영국 1,000 euros(~2026-06-29) → £800(2026-06-30~) S.I. 2026/621
한국 2027-02-19 전건화·요청 시 3영업일 추가정보를 지원하는가 금액 게이트 제거, 요청 응답 큐 시행령 §10-10 시행예정 판본
상대 VASP 실사 자료(인허가·트래블룰 이행)를 남길 수 있는가 한국 2027-02-19~ 고시 §28-2 등급 판정 감독규정 FIU 고시 제2026-2호
자기수탁 지갑 검증 방법은 무엇이고 어느 규범의 방법에 해당하는가 EU 는 1종 이상 열거, 한국 2027 은 동일인 요건만 EBA/GL/2024/11 ¶83
메시지·판단 기록을 내보낼 수 있는가 벤더 교체 시 기록 보존 —

4. 통합 vs 분리

Travel Rule + 거래모니터링 운영

KYC
  └─ Travel Rule 메시징
       └─ 거래모니터링 · 블록체인 분석
            └─ 내부 위험판단 엔진

FATF 7차 TU(2026-07-16)는 VASP 에 "transactions monitoring and blockchain analytics tools" 로 급속 이전을 탐지하라고 권고하지만, 이것은 트래블룰 메시징과 별개 통제입니다(7차 TU PDF). 이전 판의 "Chainalysis 는 VerifyVASP 합작을 통해 Travel Rule 제공", "TRM Travel Rule" 서술은 이번 조사에서 1차 확인되지 않아 뺐습니다.

실무 포인트

단일 벤더 통합은 편하지만 벤더 종속이 생깁니다. 어떤 구조든 메시지 원문·판단 근거·상대방 평가 기록을 자사 쪽에 보관해 두면 교체 비용이 줄어듭니다.

5. 한국 시장 운영 패턴

국내 VASP ↔ 국내 VASP
  ├─ ~2027-02-18: 100만원 이상만 정보제공 (in-force)
  └─ 2027-02-19~: 모든 이전 (enacted-not-in-force)
국내 VASP → 해외 VASP
  └─ 2027-02-19~: 저위험 허용 / 그 외 동일인 간만 / 고위험 제한 (고시 §28-2②)
국내 VASP → 자기수탁 주소
  └─ 2027-02-19~: 동일인 간만 허용, 위험 현저하면 제한 (고시 §28-2④)

2026 상반기 총 출고 62.8조원 중 트래블룰 적용은 9.5조원(약 15%)이었습니다(금융위 2026-10-01). 국내 사업자 간 메시지는 솔루션 네트워크를 통해 오가고, CODE 홈페이지는 VerifyVASP 를 상호운용 목록에 올리고 있습니다(B). 거래소별로 어느 네트워크를 쓰는지는 이 저장소가 1차 근거로 확인하지 않았습니다.

실무 포인트

2027-02-19 이후 해외 VASP 허용 여부는 메시지 연결뿐 아니라 상대 VASP 평가 결과로 갈립니다. 벤더가 연결을 제공해도 평가가 "그 외" 등급이면 동일인 이전만 허용됩니다.

7. 가격

이전 판의 가격 참고치(연 $20K~$1M+, 거래당 ~$0.10)는 출처가 없어 삭제했습니다. 가격은 공개되지 않으므로 견적으로만 확인할 수 있습니다.

8. 2026-10-21 기준 변화와 남은 미확인

표준

  • IVMS 101.2023 이 현행판(2023-08 발행, ISWG 2024-06-04 갱신 공표). "IVMS101 v2" 전망은 근거가 없습니다
  • DTI(ISO 24165)는 TRP 가 호환을 명시, LEI(ISO 17442)는 IVMS 101.2023 제약 C9~C11

FATF

  • R.16 개정(2025-06 총회)은 VASP 에 R.15 를 거쳐 간접 적용, 이행 기대시한 2030-12-31
  • R.16 이행 가이던스 초안 의견수렴 2026-06-24~2026-08-21, 2026-10-21 기준 최종본 미발간(proposed)
  • 이전 판의 "2026 후반 가이던스 → 모든 벤더 업데이트", "2030 발효"는 각각 낡거나 부정확한 표현이라 고쳤습니다

미확인으로 남은 것

  • 각 네트워크 회원 수·거래량 — 자사 주장만 있음
  • VerifyVASP·CODE 지분 구조, 상호 연동 완료 시점
  • 서명 표준(EIP-191/BIP-137) 사용 여부 등 자기수탁 검증 방식의 벤더별 세부

💼 실무 현장 (Industry Reality)

선택 흐름 — 우열이 아니라 상대방에서 출발

자주 나오는 오해

  • "Travel Rule 은 100만원 이상만" — 한국 ~2027-02-18 기준입니다. 2027-02-19 부터 전건이고, EU TFR 은 처음부터 금액 무관 전건입니다
  • "개인지갑 출금은 Travel Rule 과 무관" — 관할마다 다릅니다. EU 는 EUR 1,000 이상이면 자기수탁 주소 소유·통제 평가(TFR 제14조(5)·EBA GL ¶83), 영국은 reg 64G(정보 요청·미수령 시 지급 금지), 한국은 2027-02-19 부터 동일인 간만 허용(고시 §28-2④)
  • "외부지갑 등록제는 자율규제일 뿐" — 2026-10-21 기준으로는 맞지만 2027-02-19 부터 동일인 요건이 고시 의무가 됩니다
  • "GTR 은 BitGo 컨소시엄" — 운영 주체는 Infozone Technologies(싱가포르)입니다
  • "OpenVASP 는 Ethereum 기반 메시징" — OpenVASP Association 은 TRP 를 관리하는 협회입니다
  • "FIU 에 트래블룰 실패율을 분기 보고한다" — 그런 보고 의무의 근거 조문은 이 저장소가 확인하지 못했습니다

한국 특수 현실

  • 2027-02-19 전환: 정보제공 전건화, 추가정보 요청 시 3영업일, 해외 VASP 3등급, 자기수탁 동일인 요건, 1천만원 이상 자체 의심거래 감시체계가 같은 날 시작합니다(감독규정 §28-2 시행일은 기산점 문제로 미확정)
  • 제재 현실: 두나무 과태료 352억원(2025-11-06 결정)의 사유는 고객확인·거래제한·의심거래보고 위반이고 트래블룰은 포함되지 않았습니다(FIU 보도자료 KDI 미러)
  • 이전 판의 "연동 3개월 공백", "외부지갑 24h 홀드", "Notabene 한국 미진출", 거래소별 스택 표·평가, 가입 소요기간·할인율은 공개 근거가 없어 삭제했습니다

FATF 기준(INR.15 §7(b))을 가상자산 이전에 적용한 규칙. VASP 운영에서 가장 손이 많이 가는 테마 중 하나입니다. 이 글을 읽고 나면 Travel Rule 이 왜 "임계금액 하나"로 요약되지 않는지, 관할마다 금액 조문과 의무 조문이 어떻게 갈라지는지, 그리고 한국이 2027-02-19 에 무엇이 바뀌는지 이해하게 됩니다..

TL;DR

  • VASP 가 다른 VASP 에게 가상자산을 이전할 때 송신인 + 수신인 정보를 함께 전달해야 하는 의무. 국제 기준은 2019-06 채택된 INR.15 §7(b) 이고, 금액 조건이 없습니다
  • 금액 구조는 세 유형 — A 의무 자체에 금액(미국 USD 3,000 이상, 한국 ~2027-02-18 의 100만원 이상) · B 의무는 전건, 금액은 정보 깊이만(영국·싱가포르·홍콩, EU 는 변형 B′) · C 금액 없음(일본·스위스·캐나다·브라질). "임계 얼마" 한 칸으로 적으면 B·C 가 전부 틀립니다
  • 금액은 시점이 붙습니다 — 영국 심화 기준은 1,000 euros(2023-09-01~2026-06-29) → £800(2026-06-30~, S.I. 2026/621). 한국은 100만원 이상(~2027-02-18) → 전건(2027-02-19~, 대통령령 제36592호, 2026-10-21 기준 enacted-not-in-force)
  • 2026-10-21 기준 쟁점은 입법이 아니라 집행: FATF 7차 Targeted Update(2026-07-16) 응답 관할의 83%(91/109) 가 입법했지만 그중 60%(55/91) 는 트래블룰 감독·집행 조치가 한 건도 없음. 트래블룰 위반을 독립 제재 사유로 명시한 사건은 2024-01-01~2026-10-21 어느 관할에서도 확인되지 않음
  • 메시지 데이터 모델 현행판은 IVMS 101.2023(2023-08). "IVMS101 v2" 는 존재하지 않음

1. Travel Rule 이 뭐고 왜 만들어졌나

전통 금융의 유산

은행 송금에서는 이체지시에 송신인 정보가 함께 실려 갑니다. 미국의 규정 근거는 31 CFR 1010.410(f) 로, 미국 내 송신·중개 금융기관은 "transmittal of funds in the amount of $3,000 or more" 의 이체지시에 송신인 성명·계좌번호·주소·금액·실행일·수취 금융기관 정보를 포함해야 합니다(Cornell LII 31 CFR 1010.410). "돈이 움직이면 사람 정보도 같이 움직여야 한다"는 원칙이 가상자산으로 옮겨 온 것이 Travel Rule 입니다.

FATF 가 이걸 가상자산에 확장한 경로

FATF 는 R.16 을 고쳐서 가상자산에 적용한 것이 아닙니다. 2018-10 R.15 개정으로 VA·VASP 정의를 용어집에 신설하고, 2019-06 INR.15 와 RBA 가이던스 초판을 채택했습니다. 가상자산 정보 전달 의무는 INR.15 §7(b) 에 있습니다(FATF 2021 RBA 가이던스).

INR.15 §7(b) — "Countries should ensure that originating VASPs obtain and hold required and accurate originator information and required beneficiary information on virtual asset transfers, submit the above information to the beneficiary VASP or financial institution (if any) immediately and securely" — 금액 기준 없음. USD/EUR 1,000 은 §7(a) 의 CDD(임시거래) 기준입니다(FATF Recommendations).

2021-10-28 개정 RBA 가이던스가 운영 규칙을 단락 단위로 고정했습니다 — 모든 VA 이전은 국경 간 전신송금으로 취급(para 179), "즉시" 는 이전 이전·동시·병행 전송이며 "Post facto submission … should not be permitted"(para 185, 187), USD/EUR 1,000 de minimis 는 국가 선택이고 그 미만에도 성명·지갑주소는 수집(para 191–192), 상대 VASP 실사 3단계(para 196–199)(FATF 2021 RBA 가이던스).

실무 포인트

Travel Rule 은 "기술 구현 문제"로 포장되지만 본질은 VASP 끼리 고객 정보를 주고받자는 합의입니다. 2026-10-21 기준 병목은 기준이 없어서가 아니라 집행이 비어 있어서입니다 — 7차 TU 본문 para 25 는 입법 관할 91 곳 중 55 곳(60%)이 지적·지시·집행·감독조치를 하지 않았다고 적습니다(요약문의 "almost half" 가 아니라 본문 수치를 인용할 것)(FATF 7차 TU PDF).

2. 연대기 — 기준 채택에서 각국 시행까지

근거: FATF 일자는 2021 RBA 가이던스·R.16 개정 설명서·7차 TU, 각국 일자는 §3 표의 조문 링크. 홍콩 2023-06-01 은 T3 두 건 일치(B)이고, 흔히 보이는 "홍콩 2024-06-01" 은 트래블룰 일자가 아닙니다 — 기존 SFO 인가 VATP 의 12개월 과도기간 종료와 혼동된 것으로 보입니다(Clyde & Co 2023-06-07).

3. 핵심 정보 항목

FATF 문언은 "required originator information / required beneficiary information" 이라고만 하고 항목은 INR.16 정의를 따릅니다. 2025 개정 INR.16 의 항목 목록은 이 저장소가 1차 문언으로 확보하지 못했습니다. 관할별 조문으로 확인된 것만 적습니다.

EU 를 "모든 필드 필수"로 적는 경우가 많지만 TFR 제14조(1)은 주소 또는 생년월일·출생지입니다. IVMS 101.2023 의 제약 C1 도 자연인 송신인에 대해 주소(GEOG/HOME/BIZZ)·고객식별번호·국가식별번호·생년월일·출생지 중 1개 이상을 요구합니다(IVMS 101.2023 PDF). 수신 측 검증기를 "EU 는 생년월일 필수"로 짜면 적법한 메시지를 거절하게 됩니다.

4. 관할 비교 — 의무 조문과 수치 조문은 따로 읽는다

이 표를 어떻게 읽어야 하나

"임계금액"을 한 칸에 적으면 대부분의 관할이 틀립니다. 의무를 부과하는 조문과 금액을 정하는 조문이 다르고, 금액이 하는 일도 다릅니다.

  • A형 — 의무 자체에 금액이 붙는다. 기준 미만이면 Travel Rule 대상이 아닙니다. 미국, 한국(~2027-02-18), UAE(VARA).
  • B형 — 의무는 전건, 금액은 정보 깊이(또는 신원확인)만 나눈다. 영국·싱가포르·홍콩·인도네시아. EU 는 정보는 전건 동일이고 금액은 자기수탁 주소 검증만 발동하는 B′.
  • C형 — 금액이 없다. FATF·일본·스위스·캐나다·브라질, 호주(법률 단계).

  • 일본 10만엔 — 범수법 시행령 제7조1항1호의 특정거래(特定取引) 정의이며 고객확인(CDD) 을 발동시키는 기준입니다. 통지의무를 정한 법 제10조의5, 그 위임을 받은 시행규칙 제31조의7 어디에도 금액 조건이 없습니다. 문언은 「十万円を超える」 초과입니다.

호주는 한 층 더 남아 있습니다. s 66A 본문에 금액이 없는 것은 확인했지만 전달할 정보 항목은 AML/CTF Rules 에 위임돼 있고, Rules 의 금액 구분과 시행일(2026-03-31 vs 2026-07-01)은 출처끼리 상충해 확정하지 못했습니다.

룰 엔진을 만들 때는 B·C형 관할에 금액 게이트를 걸면 안 됩니다. 게이트는 "의무 발동"이 아니라 "어떤 필드를 채울 것인가"에 걸어야 합니다. 그리고 금액 기준은 반드시 유효 구간과 함께 저장해야 합니다 — 2026-06-29 이전 영국 거래를 감사할 때 £800 을 대입하면 틀린 판정이 나옵니다. 한국은 2027-02-19 부터 A형 게이트 자체가 사라집니다.

5. 메시지 표준: IVMS 101.2023

정체성

  • IVMS 101 — 송·수신인 정보 데이터 모델. 2020-05 원판은 JWG 가, 현행판 IVMS 101.2023(Issue 1 FINAL, 2023-08 발행)은 GDF·OpenVASP·VASPnet 이 2023-04 결성한 interVASP Standards Working Group(ISWG)이 유지. ISWG 는 2024-06-04 갱신을 공표(interVASP)
  • 2023판은 PayloadVersionCode(101 / 101.2023), LEI 제약(C9~C11), 주소유형 GEOG, 자연인 송신인 필수항목 제약 C1 을 정식화(IVMS 101.2023 PDF)
  • 표준 문서에는 JSON/XML 스키마가 포함되지 않습니다 — 스키마는 구현체가 별도로 관리합니다
  • "IVMS101 v2" 라는 판은 없습니다. npm 패키지 버전(ivms101@2.0.0)과 표준 판 명칭을 혼동하지 말 것

데이터 모델 상세·관할별 검증 규칙: ../4-technology/travel-rule-protocols.md §2·§N 참조.

실무 포인트

IVMS 101 은 데이터 모델일 뿐이고, 관할별 필수 항목은 각 조문이 정합니다. 같은 메시지라도 수신 측은 송신 관할의 조문 기준으로 완전성을 판정해야 합니다. EBA GL ¶24 의 기술적 한계 보완 유예는 2025-07-31 에 끝났으므로, 2025-08-01 이후 EU 에서는 필드 누락을 기술적 한계로 정당화할 수 없습니다(EBA/GL/2024/11).

6. Travel Rule 프로토콜 — 개요

표준(IVMS 101)이 "무엇을"이라면, 프로토콜은 "어떻게"입니다. 2026-10-21 공개 자료로 확인된 사실만 적습니다(벤더 간 우열 평가 없음).

  • TRP — OpenVASP Association(Zug)이 관리하는 양자 간 암호화 교환 표준. "No data or metadata is ever exchanged with any third party", ISO 24165(DTI)·IVMS101 호환(OpenVASP TRP)
  • TRISA — gRPC/protobuf 기반 오픈소스 프로토콜 + Global Directory Service. 오픈소스 노드 Envoy 가 TRISA 와 TRP 를 모두 지원(자사 페이지, B)(trisa.dev)
  • GTR — 운영 주체는 Infozone Technologies Pte. Ltd.(싱가포르)(GTR)
  • 상호운용 허브(자사 페이지, B) — CODE 홈페이지는 CodeVASP·VerifyVASP·GTR·Sumsub·Sygna·Notabene·CryptoSwift 연동을 표시(CODE), Sumsub 는 자체·GTR·CODE·TRP·Sygna 5개 프로토콜 연동을 표시(Sumsub), Notabene 는 고객별 TRP 1.0 엔드포인트를 지원한다고 밝힘(Notabene TRP)

각 네트워크의 VASP 수는 자사 주장(T5급)이라 이 저장소에서 인용하지 않습니다.

프로토콜별 상세: ../4-technology/travel-rule-protocols.md §3 참조.

실무 포인트

프로토콜 선택은 "고객의 출금 상대방이 어느 네트워크에 있나"로 결정됩니다. 어떤 네트워크도 모든 상대방을 덮지 못하므로, 상대방 미연결(sunrise) 상황의 처리 정책을 먼저 정해 두는 편이 낫습니다(§8-A).

7. 한국 시장의 Travel Rule

현행(2022-03-25 ~ 2027-02-18) — 100만원 이상, 국내 VASP 간

시행령 제10조의10 제1호는 「1백만원 이상에 상당하는 가상자산을 이전하는 경우」에 정보제공 의무를 겁니다(A형)(법제처 현행 판본). 금융위의 2026-10-01 상반기 실태조사에서 총 출고 62.8조원 가운데 트래블룰이 적용된 것은 9.5조원(약 15%) 이었습니다(금융위 2026-10-01). 100만원 기준과 국내 VASP 간 이전으로 한정된 현행 제도가 덮는 범위를 보여 주는 수치이고, 2027년 이후 비교의 기준선입니다.

국내 사업자 간 메시지는 VerifyVASP·CODE 등 솔루션 네트워크로 오갑니다. CODE 홈페이지는 VerifyVASP 를 상호운용 목록에 올리고 있습니다(B)(CODE). 운영 주체 지분 구조·연동 완료 시점은 공개 1차 근거로 확인되지 않았습니다.

2027-02-19 부터 — 전건 + 상대방 유형별 허용 규율 (enacted-not-in-force)

대통령령 제36592호(2026-08-11 국무회의 의결, 2026-08-18 공포)의 부칙 제1조 단서가 제10조의10·제10조의20 등을 「공포 후 6개월이 경과한 날」로 유예했고, 법제처 시행일 색인은 2027-02-19 를 가리킵니다(언론의 2027-02-20 은 공포일을 하루 늦게 잡은 계산으로 보임)(법제처 시행예정 판본; 금융위 2026-08-11).

8. 세 가지 핵심 난제

A. Sunrise Issue — 관할별 시행 격차

A국은 시행, B국은 미시행이면 A국 VASP 가 보낸 정보를 B국 상대방이 받을 수단이 없습니다. 규범이 허용하는 대응은 다음과 같습니다.

  • FATF 2021 가이던스 para 200–201 — 계약·사업관행으로 상대에게 준수를 요구, 내부이전 한정, 확인된 본인(first-party) 이전만 허용
  • 영국 FCA(2023-08-17) — 미시행 관할로 보낼 때 상대의 수신 가능 여부를 합리적으로 확인하고, 불가하면 정보를 수집·검증·보관한 뒤 이전 가능. 그런 관할에서 받은 정보 누락 이전은 위험기반으로 지급 여부 결정(FCA 성명)
  • EU — 거래 금지가 아니라 "고위험 요소"로 분류하고, 반복적으로 정보를 누락하는 기관은 식별 후 3개월 안에 당국에 보고(EBA GL §4.5·§4.7)
  • 한국(2027-02-19~) — 상대 VASP 의 트래블룰 이행이 저위험 허용 요건
  • 거절·보류 — 영국 reg 64C(9)(완전 준수 전 이전 금지), 싱가포르 ¶13.11(준수 불가 시 이전 실행 금지)

2030-12-31 은 sunrise 해소 목표가 아니라 개정 R.16 의 이행 기대시한입니다.

B. VASP Discovery — 지갑주소 식별

FATF 2021 가이던스 para 197(a)는 "the FATF is not aware of any technically proven means of identifying the VASP that manages the beneficiary wallet exhaustively, precisely, and accurately … from the VA address alone" 라고 인정합니다. 주소만으로는 상대 VASP 를 알 수 없다는 것이 출발점입니다.

  • EBA GL ¶77~78 — 상대 주소가 자기수탁인지 판단할 때 블록체인 분석·제3자 데이터·메시징 식별자를 쓰고, 불가하면 고객에게 직접 확인
  • 식별자 표준 — 법인은 LEI(ISO 17442, IVMS 101.2023 제약 C9~C11), 토큰은 DTI(ISO 24165, TRP 호환)
  • 7차 TU 권고 — 상대방 VASP 식별을 "completely and accurately" 수행, 소매고객으로 위장한 역외 VASP 계정 탐지

C. 개인정보 보호와의 긴장

Travel Rule 은 본질적으로 개인정보를 VASP 간에 전송합니다. EU 는 TFR 전문 19항에서 "the processing of personal data under this Regulation should take place in full compliance with Regulation (EU) 2016/679" 를, 제3국 이전은 GDPR 제5장을 따르라고 정합니다(EBA 의견수렴 결과표 인용)(EBA/GL/2024/11). 메시지 보존기간을 관할별로 정리한 공개 근거는 이 저장소에서 확인하지 못했습니다 — 각 관할 기록보존 조문을 따로 확인해야 합니다. 한국 개인정보보호위원회의 트래블룰 국외이전 관련 의결·안내도 확인되지 않았습니다.

실무 포인트

세 난제 중 실제 거래 허용 여부를 가르는 것은 A·B 입니다. 2026-10-21 기준 "트래블룰 미준수 리스크"는 제재 리스크라기보다 상대방 실사와 거래 허용 여부의 문제입니다 — 트래블룰 위반만으로 제재된 사례가 어느 관할에도 없기 때문입니다.

9. 운영 흐름 — 송신 VASP 에서 수신 VASP 까지

근거: 사후 전송 금지 FATF 2021 para 185·187, 주소 식별 한계 para 197(a), IVMS 101.2023 제약 C1, 수신 측 누락 탐지·집행·거절·보류 정책 PSN02 ¶13.12·¶13.14, EU 반복 누락 보고 EBA GL §4.7.

실무 포인트

정보 교환이 안 되면 송금 자체가 멈춥니다. 그래서 상대방별 실패 기록이 운영의 핵심 데이터입니다. EU 는 이를 "repeatedly failing" 판정 기준(정성·정량)과 보고 의무로 법제화했습니다. 미연결 상대방 비율·자동 성공률·오류 유형 분포 같은 업계 평균치는 공개 출처로 확인되지 않습니다 — 자사 로그로 기준선을 잡아야 합니다.

  • R.16 이행 가이던스 초안 — 2026-06-24 공개의견수렴, 2026-08-21 마감. 2026-10-21 기준 최종본 미발간(proposed, B)(FIAU Malta 요약)
  • 7차 Targeted Update(2026-07-16) — 트래블룰 입법 83%(91/109, 2025년 73%), 입법 관할의 60%(55/91) 조치 없음. 처음으로 VASP 에 "transactions monitoring and blockchain analytics tools" 로 급속 이전 탐지를 권고(7차 TU PDF)
  • 함께 읽을 FATF 문서 — Red Flag Indicators(2020-09-14)(PDF), 스테이블코인·비수탁지갑 보고서(2026-03-03)(FATF), 역외 VASP 보고서(2026-03-11)(FATF), DeFi 보고서(2026-07-21)(FATF)
  • 2025 개정 INR.16 의 "구조화 데이터·ISO 20022" 같은 세부 문언은 이 저장소가 원문으로 재확인하지 못했습니다

실무 포인트

개정 R.16 은 VASP 에 직접 적용되지 않고 R.15 를 거쳐 들어오므로, 실체 변화는 각국 국내법 개정 형태로 옵니다. 2026-10-26~30 FATF 총회에서 가이던스 최종본 여부가 확인될 수 있습니다. 시스템 로드맵은 FATF 일정보다 국내 시행일(한국 2027-02-19, 영국 reg 34A 2027-02-01)에 맞추는 편이 정확합니다.

□ 관할별 금액 기준을 유효 구간(valid_from~valid_to)과 함께 저장 — 영국 €1,000→£800, 한국 100만원→전건

한국 — 2027-02-19 전환 준비

  • 기준선: 2026 상반기 총 출고 62.8조원 중 트래블룰 적용 9.5조원(약 15%)(금융위 2026-10-01). 전건화 이후 메시지 처리량이 크게 늘어날 수 있는 구조입니다
  • FIU 계획: 2026-02-05 업무계획에 트래블룰을 100만원 미만 거래와 수신거래소로 확대하는 방안이 들어 있었습니다(금융위 2026-02-05)
  • 제재 현실: FIU 가 2025-11-06 두나무에 결정한 과태료 352억원의 사유는 고객확인·거래제한·의심거래보고 위반이었고 트래블룰(특금법 제5조의3)은 포함되지 않았습니다(FIU 보도자료 KDI 미러)

자주 나오는 오해

  • "Travel Rule = 분석 도구" — 블록체인 분석(노출도·주소 귀속)과 트래블룰 메시징은 별개 시스템입니다. FATF 7차 TU 는 전자를 "transactions monitoring and blockchain analytics tools" 로, 후자를 R.15/INR.15 의무로 따로 다룹니다
  • "100만원 미만은 신경 안 써도 됨" — 2027-02-19 부터 틀립니다(전건). 그 전에도 FIU 업무계획은 미만 거래 확대를 검토했습니다
  • "외부지갑 등록은 규제 요구사항이 아님" — 2026-10-21 기준으로는 맞지만, 2027-02-19 부터 틀립니다. 시행령 §10-20 ⑧·고시 §28-2④ 가 동일인 요건을 의무화합니다
  • "영국 트래블룰 기준 £800" — 2026-06-30 이후에만 맞습니다. 2023-09-01~2026-06-29 는 1,000 euros 였고, £800 은 의무 발동이 아니라 정보 심화 기준입니다
  • "홍콩 트래블룰 2024-06-01 시행" — 2023-06-01 시행(즉시전송 2024-01-01)입니다(B)
  • "미국이 기준을 $250 또는 $1,000 으로 낮춘다" — $250 안은 2025-04-16 철회됐고 $1,000 안은 존재가 확인되지 않습니다
  • "FATF 2030 년 발효" — 2030-12-31 은 개정 R.16 의 이행 기대시한입니다. VASP 의무의 근거(INR.15 §7(b))는 2019-06 부터 있었습니다
